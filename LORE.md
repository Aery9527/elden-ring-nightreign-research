# LORE

## Overview

- Knowledge about the game `ELDEN RING NIGHTREIGN`, and research records of specific values that the game does not state.

## Project Ground Rules

- AI agent documents MUST stay bilingual with equivalent content (the file without a suffix is the English version), for example SKILL.md = SKILL_ch.md, AGENTS.md = AGENTS_ch.md, and so on.
- Links in AI agent documents MUST match the document's language: an English file links to the English target, and a Traditional Chinese file links to the _ch target when one exists.
- The site is published with Netlify. [netlify.toml](netlify.toml) publishes the `public/` directory with no build command:
  - All site files (HTML, CSS, images) go under `public/`; files outside `public/` do not appear on the site.
  - Pages link to each other with relative paths to `.html` files and do not rely on Netlify pretty URLs.
  - Pages load game data with `fetch`, so preview them locally through an HTTP server (for example `python -m http.server -d public`); a page opened directly as a local file (`file://`) cannot load the data.
  - When adding a topic page, also add a row to its topic's table on the home page [public/index.html](public/index.html); a new topic gets its own `h2` chapter there.
  - When a page is renamed or merged into another page, add a 301 redirect from the old path in [netlify.toml](netlify.toml) and keep the old heading ids so old anchors still work. When a published section moves to another page, map its "page#id" to the new page in the old-anchor table (`moved`) of [public/nav.js](public/nav.js); when a section is removed or merged within the same page, keep its old id on the element that takes over its content.
  - Every page loads [public/nav.js](public/nav.js) before [public/render.js](public/render.js), so the header exists before rendered content scrolls to the URL anchor, and uses the same sticky `<header class="site-header">` markup as the existing pages. The header is the site-wide navigation: from any chapter the reader can see every chapter of the page and jump to it without returning to the top, so pages MUST NOT keep a hand-written table of contents. The script builds both header rows from the page itself:
    - Breadcrumb row: the site home, the page `h1` (omitted on the home page, where the home link already names the page), and the `h3` the reader is currently in, each linking to the top of that level.
    - Chapter row: every `h2` of the page in document order, named by its rendered text, with the current chapter marked by `aria-current="location"` and no chapter marked in the introduction before the first `h2`. On wide screens the row wraps so every chapter stays visible; at 640px and narrower, or 500px and shorter (a phone held sideways), it is a single row that scrolls horizontally with a visible scrollbar, and the current chapter is scrolled into view unless keyboard focus is inside the row.
    - Each page divides its content into `h2` chapters, so the chapter row lists the page's major sections. Only `h2` and `h3` headings with an `id` appear in the header, so every section heading MUST have an `id`.
  - Every source the site cites is listed once in the "資料來源" chapter (`#sources`) of the home page [public/index.html](public/index.html); topic pages MUST NOT have their own sources section, and relic tables MUST NOT have a source column. When a page starts citing a new source, add or update its row in that table. Inline citation links in body text and the source names shown for conflicting candidates stay on the pages.

## Game Data Rules

- The site reads game values (numbers and rule tags), the effect, stat, and category names that the placeholders render, and their sources only from `public/data/`; maintenance inputs that produce part of these files live in `tools/` (see Relic Data Generation):
  - [public/data/common.json](public/data/common.json): game version, stats, icons, characters, tags (`tags`), interface text (`labels`), and sources shared by all pages.
  - `public/data/relics/<category>.json`: one file per top category of the in-game relic filter (`general`, `character`, `armament`, `demerit`), holding that category, its subcategories, and its effects.
  - `public/data/armaments/weapons.json` and `public/data/armaments/spells.json`: weapons and spells keyed by their in-game ID (the `EquipParamWeapon` row, or the spell ID a weapon slot references), each with `name` (`zh` and `en`, or `null` when no source names it), `icon`, `tags`, and sources. A weapon also keeps its `sortId` and, when it carries spells, `spells` mapping each slot (`R1`, `R2`) to a spell ID. Every weapon row stays its own item even when it shares a `sortId` with another row; an unnamed row is never given another row's name.
  - Data for another game topic goes in its own file or directory under `public/data/` named after the topic and split by the game's own grouping, as `relics/` follows the in-game relic filter; definitions shared by several topics stay in `common.json`.
  - Each page lists the files it loads in `<body data-load>`, for example `common relics/general`. [public/render.js](public/render.js) stops with an error on a duplicate effect key, effect or tier `gameId`, or subcategory key; it MUST NOT let a later file override an earlier one.
- HTML holds `data-*` placeholders that [public/render.js](public/render.js) fills in; game values, including those in body-text examples, MUST NOT be hard-coded in HTML. Body prose (for example character names) and selection keys in `data-*` attributes (for example tier or level numbers) may stay in HTML.
- Value states:
  - A plain value is what the effect's `sources` report.
  - `null` means unverified; it MUST NOT be treated as 0 or false.
  - `{ "conflict": [{ "value": ..., "sources": [...] }] }` means the sources disagree; keep every candidate and never default to one.
  - These states apply to every field, including rule fields such as `stacking.stacks`; a calculation runs only when every rule it needs is explicitly satisfied, and otherwise shows the blocking state.
  - `sourcesFor` maps a field path (for example `stacking.combine`) to its sources and replaces the effect's `sources` for that field.
- Store percentages as signed numbers (for example `10`, `-5`); code derives multipliers.
- An effect with +1/+2/+3 tiers is one effect with a `tiers` array; each tier keeps its in-game `gameId`. A tier without a `+N` suffix in its name is `tier: 0`. A rule field that differs between tiers is stored on each tier instead of on the effect.
- Record each effect's resource change as the source states it; do not derive it from a universal per-point conversion.
- Tags classify game items so relic effects can be matched against them. Their definitions live in `tags` of [public/data/common.json](public/data/common.json), grouped by dimension (`weaponType`, `spellType`, `spellSchool`); each tag is `{ "name": { "zh", "en" }, "param": <value> }`, where `param` is the game param value the tag stands for (`EquipParamWeapon.wepType`, `Magic.ezStateBehaviorType`, `Magic.subCategory1`/`subCategory2`). Weapon type names are the in-game relic filter subcategory names; spell type and school names are excerpts of in-game relic effect names (for example 卡利亞劍 from 強化卡利亞劍的魔法). A spell school is defined only when a relic effect targets it.
  - An item stores `tags` as `{ <dimension>: [...] }`: a list of tag keys, where an empty list means checked with no defined tag; `null` means unverified; a `conflict` keeps every candidate.
  - A relic effect's `targets` uses the same dimensions, for example `{ "spellType": ["sorcery"], "spellSchool": ["carian-sword"] }`. An item matches when, for every dimension in `targets`, its tags share at least one key (AND across dimensions, OR within one); a dimension the effect does not list is not checked. A known mismatch in any listed dimension is a mismatch; otherwise an unverified listed dimension makes the match unverified, and a conflicting one shows the conflict.
  - `targets` covers only direct attack-power boosts whose param pattern is verified (see Relic Data Generation). A match means the effect's attack-power multiplier applies to that item category; it says nothing about healing, buffs, ailment buildup, or other mechanics. An effect without `targets` is not modeled, which is not the same as matching nothing.
- Relic effects follow the in-game relic filter tree: every effect has a `subcategory`, and each category and subcategory keeps its in-game param `gameId`. A category Chinese name not taken from game text is a site translation, and pages MUST say so.
- Every effect has `name` (`zh` and `en`) and `icon`. `icon: null` means no in-game image that meets the image rules exists; it MUST NOT be replaced with a different image.
- Effect rows of a relic table are rendered from data with `<tbody data-relic-table="<subcategory>">`; effect rows MUST NOT be hand-written in HTML. In the effect column the detail comes first, followed by the rule line; the value line built from structured values (`modifier`) appears only for an effect without a detail, because the detail already states the same numbers. Conflicting candidate values are always listed with their sources. An effect with neither a detail nor structured values shows 未載明數值 in its tone. The rule line omits availability, which the 種類 column shows, and the self-stacking of a buff, which its tone shows; blue also means multiple copies add, so a buff's combine rule is listed only when it is not `add`, and its across-tier rule only when it is not `true`; conflicting self-stacking is still listed with its candidates. Demerit effects are always red, so their rule line keeps the self-stacking state. The 種類 column shows 一般 and/or 深層 from `availability`, or the icon and name of each relic for a fixed-relic effect (`relics`); when a tiered effect appears in more than one kind, every line lists the tiers of that kind (for example 一般：+1、+2、+3 and 深層：+3), and a tiered effect in a single kind shows only the kind (for example 一般); unverified or conflicting availability shows its status.
- [public/render.js](public/render.js) colors data-generated detail lines, value lines, and body-text examples by tone: effects in the demerit category are red (`tone-debuff`); other effects are blue when they stack with themselves (`stacks: true`, `tone-stack`) and green when they do not (`stacks: false`, `tone-solo`); unverified or conflicting stacking keeps the default color in bold (`tone-unverified`). In relic tables, every rule label whose state is unverified or conflicting, and the 來源分歧 label of conflicting candidate values, is also bold (`tone-unverified`). A rule-line equivalent value (for example "equals Vigor +5") takes the effect's tone. Penalty phrases listed for a detail are red inside its tone. The rule label stating that a curse effect is required (`requiresCurse: true`) is red. Each relic page shows a color legend fixed to the bottom of the viewport (`<aside class="tone-legend" data-legend>`), rendered from `legend` in [public/data/common.json](public/data/common.json): each item has a `tone` (the class suffix), a `label`, and a `tip` shown on hover or focus; the items are 不可疊加 (green), 可疊加 (blue), 負面 (red), and 未核實 (bold). Tone classes MUST NOT be set by hand in HTML.
- When every tier detail of an effect ends with the same parenthetical note (for example （不適用於隱士、復仇者、執行者）), the page removes the note from each tier line and shows it once after them as 各等級：<note>; the data keeps the full text.
- `detail` holds the community detail text of an effect or tier: `en` is the source text verbatim and `zh` its translation. A detail whose number, item, or location contradicts the pinned game params is instead rewritten from the params in both languages and carries its own `sources`. An effect the dataset gives no detail gets one written from the params only when an explicit reference chain from its AttachEffectParam row gives the numbers and the detail tells the reader more than the name; otherwise it has no detail.

## Relic Data Generation

- `public/data/relics/*.json` are generated by [tools/import-relics.mjs](tools/import-relics.mjs) (`node tools/import-relics.mjs [category ...]`, run from the repo root); they MUST NOT be edited by hand. Edit the inputs and rerun:
  - [tools/relics-config.json](tools/relics-config.json): the pinned commit of each source, the category tree, the nightfarer columns, the status icon ID → icon key map (`null` = no matching licensed image), and the relic icon ID → icon key map.
  - [tools/relics-curated.json](tools/relics-curated.json): hand-curated effects matched to generated effects by `gameId`; their fields override generated values, and the script prints every overridden difference.
  - [tools/relic-details-zh.json](tools/relic-details-zh.json): the Traditional Chinese translation of each community detail, keyed by `gameId` and stored with its English original.
  - [tools/relic-stacking.json](tools/relic-stacking.json): self-stacking values for tiers the dataset leaves unknown, keyed by `gameId`, taken only from a community source that states them explicitly (the community sheet or Fextralife); each entry stores `stacks` (a boolean, or a `conflict` when the sources disagree), `sources`, and the quoted source rows in `quotes`. The script fills only unknown values and lists the sources in the effect's `sourcesFor["stacking.stacks"]`, together with the source of any tier the dataset already gives.
  - [tools/relic-details-params.json](tools/relic-details-params.json): details written from the game params, keyed by `gameId`; each entry stores the community `source` text (`null` when the dataset has no detail), the rewrite in `en` and `zh`, the param evidence in `params`, and optional `sources` (default `game-params`). A `gameId` MUST NOT appear in both detail files.
  - [tools/relic-penalties.json](tools/relic-penalties.json): penalty phrases inside the Traditional Chinese detail of a buff effect, keyed by the `gameId` that owns the detail; each value is an array of exact substrings (for example `"生命力 -5"`), written to `detail.penalties`. List every penalty in a detail, including each level's number.
- The script stops without writing when a curated effect, translation, effect or relic icon, character, or source reference (`sources`, `sourcesFor`, conflict candidates) has no match; when two curated effects map to the same `gameId`s; when a source field has an unknown enum value; when the English original of a translation or the `source` of a param rewrite differs from the source; when a `gameId` has both a translation and a param rewrite; when a param rewrite lacks `en`, `zh`, or `params`, has an empty `sources`, or has no matching effect; when an effect stores a rule field (`availability`, `requiresCurse`, `stacking`, `targets`) both on the effect and on a tier; when an effect matches more than one `targets` pattern; when a stacking entry has no matching effect, targets a tier the dataset already gives, cites a source other than the community sheet or Fextralife, lacks one quote per source, or has an invalid `stacks` (a conflict needs at least two boolean candidates with different values, each citing listed sources); when a penalty entry is not a non-empty array of non-empty strings, has no matching detail, lists a phrase missing from the detail, or lists a phrase ending in a digit that matches only part of a longer number not covered by a longer listed phrase; or when either detail file, the stacking file, or the penalty file repeats a key or differs from its canonical `JSON.stringify` output with 2-space indentation. Fix the input instead of bypassing the check.
- The script generates `targets` from the SpEffectParam rows referenced by each effect's `passiveSpEffectId_1`–`_3` whose `physicsAttackRate` is above 1: a `triggerOnWepType` gives a `weaponType`; a `magicSubCategoryChange1` with exactly one of `magParamChange` (sorcery) and `miracleParamChange` (incantation) set gives a `spellType` and a `spellSchool`; exactly one of those flags with no school and no weapon type gives a `spellType`. Only param values defined in `tags` produce a tag, and other effects get no `targets`. `targets` is a rule field: it is stored on the effect when every tier has the same value, otherwise on each tier, and its source is recorded as `sourcesFor.targets: ["game-params"]`. The script stops when an effect matches more than one pattern.
- To update a source, change its commit in the config, rerun the script, and review the printed differences and the changed translations before committing. After a game param update, check every param rewrite against the new params.
- Translating a detail:
  - Every number keeps identical digits; never compute, round, or convert units.
  - Use the effect's official Chinese name and game terms; a term with no official Chinese name stays in English.
  - Translate source notes such as `TODO` as `（原文註記：……）`; where the source contradicts the effect name, translate literally and add `（原文如此）`. MUST NOT correct the source in a translation; a contradiction with the game params goes to the param rewrite file instead.

## Armament Data Generation

- `public/data/armaments/*.json` are generated by [tools/import-armaments.mjs](tools/import-armaments.mjs) (`node tools/import-armaments.mjs`, run from the repo root); they MUST NOT be edited by hand. Both import scripts read the pinned sources of [tools/relics-config.json](tools/relics-config.json) through [tools/sources.mjs](tools/sources.mjs), so relics, weapons, and spells always come from the same game params.
  - Weapons: every `EquipParamWeapon` row whose ID is a multiple of 10000, whose `wepType` has a `weaponType` tag, that has a name, and whose `sortId` is not 9999999; plus every row that carries a spell (`equippedSpell_R1`/`equippedSpell_R2`), named or not.
  - Spells: every ID a weapon spell slot references. `spellType` comes from `Magic.ezStateBehaviorType`, and `spellSchool` from `Magic.subCategory1`/`subCategory2`, keeping only values with a defined tag (`[]` when none). A referenced ID with no `Magic` row gets `null` for both and is never classified from its name, its carrier, or the base-game list it appears in.
  - Names: the game params carry no names and no Nightreign text for weapons or spells is available, so names come from Elden Ring base-game text pinned as `erText` (soarqin/ERTools): weapons from `WeaponName` by weapon ID; spells only from the base-game sorcery and incantation lists by ID, never from `GoodsName`, whose IDs collide with key items. Blank, `%null%`, and `[ERROR]` entries are not names. An item without a name in both languages has `name: null`. Names record `sourcesFor.name: ["er-base-text"]`, and pages MUST say they are base-game reference names not confirmed for Nightreign.
  - Icons: the script looks up `File:ER SB Icon <weapon|shield|Spell> <English name without colons>.png` on Eldenpedia (`shield` for the three shield types) and sets `icon: { "src", "page" }` only when the file exists and its page carries `{{License|game}}`; otherwise `icon: null`. Lookups are cached in `tools/.cache/eldenpedia/files.json`. Afterwards run `python tools/fetch-icons.py`, which downloads every referenced icon missing from `public/images/` and downscales it to 96px.
- The script stops without writing the data files when a name exists in only one language, a carried spell is not included, a spell-carrying weapon's `wepType` has no tag, a spell's `ezStateBehaviorType` has no tag, two icons share a file name, or a source it cites is missing from common.json.

## Game Writing Rules

- When linking to an external resource, open it in a new window; navigating away from the current page is forbidden.
- Follow responsive web design (RWD) principles and support phones, tablets, desktops, and other devices.
- When mentioning an in-game item, agents MUST find the corresponding in-game image. The image source is [Eldenpedia](https://eldenring.wiki.gg/).
  - Use only images whose file page marks the license as a game asset (`{{License|game}}`); community edits (for example, filenames containing `Custom`) do not count as in-game images.
  - Download images to `public/images/`; the home page sources list their wiki file pages. An image larger than 96px may be downscaled to 96px; no other edits are allowed.
  - Each icon in [public/data/common.json](public/data/common.json) records its wiki file page in `page`; weapon and spell icons are stored in their item's `icon` in `public/data/armaments/` instead (see Armament Data Generation). The home page lists the file pages of every icon in common.json with `<span data-icon-sources>`, and states once that weapon and spell icons come from the Eldenpedia ER SB Icon series, whose file pages stay in the item data.
  - Images in the same layout position MUST keep the same size. Every image uses the `.icon` class, and its size is set only in `public/styles.css` by position, never adjusted on an individual image:
    - Inside a table: 48px (`td .icon`).
    - In a name list inside a table entry, including the 種類 column: 24px (`td .entry .icon`).
    - In body text: 24px (`.icon`).
    - When a new layout appears, first add a size rule for that position in `public/styles.css`.
    - The `width`/`height` attributes of `<img>` match the size for its position.
