# LORE

## Overview

- Knowledge about the game `ELDEN RING NIGHTREIGN`, and research records of specific values that the game does not state.

## Project Ground Rules

- AI agent documents MUST stay bilingual with equivalent content (the file without a suffix is the English version), for example SKILL.md = SKILL_ch.md, AGENTS.md = AGENTS_ch.md, and so on.
- Links in AI agent documents MUST match the document's language: an English file links to the English target, and a Traditional Chinese file links to the _ch target when one exists.
- The site is published with Netlify. [netlify.toml](netlify.toml) publishes the `public/` directory with no build command:
  - All site files (HTML, CSS, images) go under `public/`; files outside `public/` do not appear on the site.
  - Pages link to each other with relative paths to `.html` files and do not rely on Netlify pretty URLs.
  - Pages load game data with `fetch`, so preview them locally through an HTTP server (for example `python -m http.server -d public`); a page opened directly as a local file (`file://`) cannot load the data.
  - When adding a topic page, also add a row to its topic's table on the home page [public/index.html](public/index.html); a new topic gets its own `h2` chapter there.
  - When a page is renamed or merged into another page, add a 301 redirect from the old path in [netlify.toml](netlify.toml) and keep the old heading ids so old anchors still work. When a published section moves to another page, map its "page#id" to the new page in the old-anchor table (`moved`) of [public/nav.js](public/nav.js); when a section is removed or merged within the same page, keep its old id on the element that takes over its content.
  - Every page loads [public/nav.js](public/nav.js) before [public/render.js](public/render.js), so the header exists before rendered content scrolls to the URL anchor, and uses the same sticky `<header class="site-header">` markup as the existing pages. The header is the site-wide navigation: from any chapter the reader can see every chapter of the page and jump to it without returning to the top, so pages MUST NOT keep a hand-written table of contents. The script builds both header rows from the page itself:
    - Breadcrumb row: the site home, the page `h1` (omitted on the home page, where the home link already names the page), and the `h3` the reader is currently in, each linking to the top of that level. On narrow screens the row wraps instead of scrolling horizontally.
    - Chapter row: every `h2` of the page in document order, named by its rendered text, with the current chapter marked by `aria-current="location"` and no chapter marked in the introduction before the first `h2`. On wide screens the row wraps so every chapter stays visible. At 640px and narrower, or 500px and shorter (a phone held sideways), the row becomes a button that names the current chapter (章節：<chapter>, or 本頁章節 in the introduction); the button opens the chapters as a vertical menu below the header and over the content, which scrolls inside itself when it is too long and opens with the current chapter in view. Choosing a chapter, pressing Escape, or clicking outside the menu closes it.
    - Each page divides its content into `h2` chapters, so the chapter row lists the page's major sections. Only `h2` and `h3` headings with an `id` appear in the header, so every section heading MUST have an `id`.
  - Every source the site cites is listed once in the "資料來源" chapter (`#sources`) of the home page [public/index.html](public/index.html); topic pages MUST NOT have their own sources section, and relic tables MUST NOT have a source column. When a page starts citing a new source, add or update its row in that table. Inline citation links in body text and the source names shown for conflicting candidates stay on the pages.

## Game Data Rules

- The site reads game values (numbers and rule tags), the effect, stat, and category names that the placeholders render, and their sources only from `public/data/`; maintenance inputs that produce part of these files live in `tools/` (see Relic Data Generation):
  - [public/data/common.json](public/data/common.json): game version, stats (`stats`), icons, characters, tags (`tags`), interface text (`labels`), and sources shared by all pages.
  - `public/data/relics/<category>.json`: one file per top category of the in-game relic filter (`general`, `character`, `armament`, `demerit`), holding that category, its subcategories, and its effects.
  - `public/data/armaments/weapons.json` and `public/data/armaments/spells.json`: weapons and spells keyed by their in-game ID (the `EquipParamWeapon` row, or the spell ID a weapon slot references), each with `name` (`zh` and `en`, or `null` when no source names it), `icon`, `tags`, and sources. A weapon also keeps its `sortId` and, when it carries spells, `spells` mapping each slot (`R1`, `R2`) to a spell ID. A named weapon also keeps raw param values (see Armament Data Generation): `attack` (`physical`, `magic`, `fire`, `lightning`, `holy`), `scaling` (keyed by the `stats` keys `strength`, `dexterity`, `intelligence`, `faith`, `arcane`), `critical`, `passive` (`zh` and `en`, or `null`), and `buildup` (ailment key to value, `{}` when none). A spell with a `Magic` row also keeps raw cost params: `cost` (`fp`, `stamina`) and `chargeCost` (`fp`, `stamina`, or `null`). Every weapon row stays its own item even when it shares a `sortId` with another row; an unnamed row is never given another row's name.
  - Data for another game topic goes in its own file or directory under `public/data/` named after the topic and split by the game's own grouping, as `relics/` follows the in-game relic filter; definitions shared by several topics stay in `common.json`.
  - Each page lists the files it loads in `<body data-load>`, for example `common relics/general`. [public/render.js](public/render.js) tells a relic category file (`category`), a weapon file (`weapons`), and a spell file (`spells`) apart and stops with an error on any other file; it stops on a duplicate effect key, effect or tier `gameId`, subcategory key, weapon ID, or spell ID (each kind checked on its own), on an item tag or effect `targets` key not defined in `tags`, on an effect `stats` key or a stat `base` not defined in `stats`, and, when spells are loaded, on a carried spell or a `targets.spell` ID that is missing; it MUST NOT let a later file override an earlier one.
- HTML holds `data-*` placeholders that [public/render.js](public/render.js) fills in; game values, including those in body-text examples, MUST NOT be hard-coded in HTML. Body prose (for example character names) and selection keys in `data-*` attributes (for example tier or level numbers) may stay in HTML.
- Value states:
  - A plain value is what the effect's `sources` report.
  - `null` means unverified; it MUST NOT be treated as 0 or false.
  - `{ "conflict": [{ "value": ..., "sources": [...] }] }` means the sources disagree; keep every candidate and never default to one.
  - These states apply to every field, including rule fields such as `stacking.stacks`; a calculation runs only when every rule it needs is explicitly satisfied, and otherwise shows the blocking state.
  - `sourcesFor` maps a field path (for example `stacking.combine`) to its sources and replaces the effect's `sources` for that field.
- Store percentages as signed numbers (for example `10`, `-5`); code derives multipliers.
- An effect with +1/+2/+3 tiers is one effect with a `tiers` array; each tier keeps its in-game `gameId`. A tier without a `+N` suffix in its name is `tier: 0`. A rule field that differs between tiers is stored on each tier instead of on the effect.
- Record each effect's resource change as the source states it; do not derive it from a universal per-point conversion.
- Tags classify game items so relic effects can be matched against them. Their definitions live in `tags` of [public/data/common.json](public/data/common.json), grouped by dimension (`weaponType`, `spellType`, `spellSchool`); each tag is `{ "name": { "zh", "en" }, "param": <value> }`, where `param` is the game param value the tag stands for (`EquipParamWeapon.wepType`, `Magic.ezStateBehaviorType`, `Magic.subCategory1`/`subCategory2`). Weapon type names are the in-game relic filter subcategory names; spell type and school names are excerpts of in-game relic effect names (for example 卡利亞劍 from 強化卡利亞劍的魔法). A spell school is defined only when a relic effect targets it.
  - An item stores `tags` as `{ <dimension>: [...] }`: a list of tag keys, where an empty list means checked with no defined tag; `null` means unverified; a `conflict` keeps every candidate.
  - A relic effect's `targets` uses the same dimensions, for example `{ "spellType": ["sorcery"], "spellSchool": ["carian-sword"] }`, plus `spell`, a list of spell IDs that names individual spells; a spell is matched against `spell` by its own ID, so `spell` is not defined in `tags` and not stored in a spell's `tags`. An item matches when, for every dimension in `targets`, its tags share at least one key (AND across dimensions, OR within one); a dimension the effect does not list is not checked. A known mismatch in any listed dimension is a mismatch; otherwise an unverified listed dimension makes the match unverified, and a conflicting one shows the conflict.
  - `targets` records the item categories or items that a game param field or a verified reference chain of the effect names (see Relic Data Generation). A match only means that param relation exists; how the effect works, when it triggers, and its limits are stated by the effect itself. An effect without `targets` is not modeled, which is not the same as being unrelated.
- A relic effect's `stats` lists, in `stats` order, the keys of `stats` in [public/data/common.json](public/data/common.json) whose value a game param field of the effect changes (see Relic Data Generation). Each stat's `param` maps a param table (`SpEffectParam`, `HeroStatusParam`) to a non-empty list of the fields that change it, and a change in any one of them counts; `poise` maps to `toughnessDamageCutRate`, the rate of poise damage taken. `attackPower` groups the five attack rates (`physicsAttackRate`, `magicAttackRate`, `fireAttackRate`, `thunderAttackRate`, `darkAttackRate`), `damageNegation` the eight damage cut rates (`slash`, `blow`, `thrust`, `neutral`, `magic`, `fire`, `thunder`, `dark` + `DamageCutRate`), and `ailmentResistance` the seven resist points (`change` + `Poison`, `Disease`, `Blood`, `Freeze`, `Sleep`, `Madness`, `Curse` + `ResistPoint`). A cap stat (`maxHp`, `maxFp`, `maxStamina`) has `base`, the base stat that also changes it (`vigor`, `mind`, `endurance`). As with `targets`, a match only means the param relation exists, an effect without `stats` is not modeled, and `stats` is a rule field. `stats` comes only from the game params, so it has no unverified or conflicting state: [public/render.js](public/render.js) stops with an error when it is not a list.
- Relic effects follow the in-game relic filter tree: every effect has a `subcategory`, and each category and subcategory keeps its in-game param `gameId`. A category Chinese name not taken from game text is a site translation, and pages MUST say so.
- Every effect has `name` (`zh` and `en`) and `icon`. `icon: null` means no in-game image that meets the image rules exists; it MUST NOT be replaced with a different image.
- The weapons page (`weapons.html`), the sorceries page (`sorceries.html`), and the incantations page (`incantations.html`) render their chapter names, chapter effects, and rows from data; the HTML holds only the chapter skeleton, and names and rows MUST NOT be hand-written:
  - Weapons page: one `<section data-weapon-type="<type>">` per `weaponType` tag, with the `h2` id `weapon-type-<type>`; the page stops with an error unless every tag has exactly one chapter. The chapter table lists the named weapons of that type by `sortId` with the columns 基礎攻擊 and 能力補正 (one line per non-zero value, named by the attack labels and the stat names) and 特殊效果 (致命補正 <value> when `critical` is not 1, the value of most weapons; then the `passive` name; then 命中累積<ailment> <value> per `buildup` entry); an empty cell shows —, which only means the stored fields have nothing, not that the weapon has no other effect. These values come only from the game params, so they have no unverified or conflicting state: a missing or extra key, or a value that is not a number, stops the page. The page states that the values are raw params, not in-game displayed values. Each row has the id `weapon-<id>`, the target of the 相關武器與法術 links on the relic pages. The `h1` keeps the id `weapons`, and the `#limitations` chapter holds `<tbody data-unlisted-spells>`: every referenced spell whose type is unverified or conflicting, with its type, school, carriers, and 相關遺物詞條 column. These spells are never classified from their name or carrier.
  - Sorceries and incantations pages: `<section data-spell-type="<type>">` is the type chapter (`h2` id `sorceries` or `incantations`), listing only the effects whose `targets` match the type alone. Each `<section data-spell-type="<type>" data-spell-school="<school>">` is a school chapter (`h2` id `spell-school-<school>`); an empty school is the 無已定義系別 chapter (`h2` id `<type>-no-school`). A school chapter lists, by ID, the spells of that type whose `spellSchool` is exactly that school (`[]` for the empty one), with the columns FP 消耗 and 耐力消耗 (the `cost` value, then 蓄力參數 <value> from `chargeCost` when it is not `null`) and 搭載法器; each row has the id `spell-<id>`. A spell on these pages whose `cost` is not two numbers, or whose `chargeCost` is neither `null` nor two numbers, stops the page. The page stops with an error unless every spell of the type appears in exactly one chapter. A spell belongs to the sorceries or incantations page when its `spellType` holds exactly that one type, and to the weapons page otherwise; a `spellType` list without exactly one key stops the page.
  - Related effects are matched by the rules above and shown in layers, so an effect appears only at the highest layer that matches: the type chapter, then the school chapter (effects that also match the type alone are omitted), then the spell row, below the spell name (effects that also match the school chapter are omitted, which leaves `spell` targets). A weapon chapter lists the effects matching its `weaponType`. Chapters and rows show 相關遺物詞條（依參數關聯） followed by effect links; effects whose match is unverified or conflicting are shown only as a bold count; a chapter with no match shows 本次建模範圍內無符合詞條, and a spell row with no own match shows nothing. It is computed on the page, which loads all four relic category files and both armament files, and no reverse list is stored in the data. A match only means the param relation exists, not that the effect applies to every item of the chapter. The 搭載法器 column lists named carriers with the slots (`R1`, `R2`) that hold the spell, and unnamed carriers only as a count of distinct weapon IDs per slot. `targets` stored on tiers is not rendered yet: the page stops with an error instead of merging tier results.
  - `armaments.html`, the former combined page, redirects to `weapons.html` in [netlify.toml](netlify.toml); the browser keeps the anchor. On the weapons page, [public/nav.js](public/nav.js) moves `#sorceries` and `#incantations` to the new pages, and [public/render.js](public/render.js) moves a `#spell-<id>` the page does not hold to the page of that spell's type, so old anchors still work. The removed weapons Dryleaf Arts and Dane's Footwork keep their `weapon-<id>` ids on their names in the inclusion-rule item of the limitations section.
- On the attributes page, the 相關遺物詞條 column of each stat row (`<td data-stat-effects="<stat>">`) lists the relic effects whose `stats` hold that stat, each linked to its effect row; a cap row then lists, under 經由<base stat name>, the effects whose `stats` hold its `base` but not the cap. It is computed on the page, which loads all four relic category files, and no reverse list is stored in the data. `stats` stored on tiers is not rendered yet: the page stops with an error. Each stat row has the id `stat-<stat>`, the target of the 相關能力值 links on the relic pages.
- Effect rows of a relic table are rendered from data with `<tbody data-relic-table="<subcategory>">`; effect rows MUST NOT be hand-written in HTML. In the effect column the detail comes first, followed by the rule line; the value line built from structured values (`modifier`) appears only for an effect without a detail, because the detail already states the same numbers. Conflicting candidate values are always listed with their sources. An effect with neither a detail nor structured values shows 未載明數值 in its tone. The rule line omits availability, which the 種類 column shows, and the self-stacking of a buff, which its tone shows; blue also means multiple copies add, so a buff's combine rule is listed only when it is not `add`, and its across-tier rule only when it is not `true`; conflicting self-stacking is still listed with its candidates. Demerit effects are always red, so their rule line keeps the self-stacking state. The 種類 column shows 一般 and/or 深層 from `availability`, or the icon and name of each relic for a fixed-relic effect (`relics`); when a tiered effect appears in more than one kind, every line lists the tiers of that kind (for example 一般：+1、+2、+3 and 深層：+3), and a tiered effect in a single kind shows only the kind (for example 一般); unverified or conflicting availability shows its status. For an effect with `targets`, the effect column then shows 相關武器與法術: the named weapons (by `sortId`) and named spells (by ID) whose tags match `targets` by the matching rules above with the result true, each with its icon and name and linked to its row (`weapons.html#weapon-<id>`, or `#spell-<id>` on the page of the spell's type as above). Unverified or conflicting matches and unnamed items are not listed, and the line is omitted when nothing is listed. A value that is not a list, or `targets` stored on a tier, stops the page with an error. A relic page with `targets` loads `armaments/weapons` and `armaments/spells`, stops with an error when either is missing, and says the names are base-game reference names. The last line of the effect column, shown only for an effect with `stats`, is 相關能力值 followed by the icon and name of each stat in `stats` order, each linked to its attributes page row (`attributes.html#stat-<stat>`); it lists only the keys in `stats`, without adding a cap from its `base`, and `stats` stored on tiers stops the page with an error.
- [public/render.js](public/render.js) colors data-generated detail lines, value lines, and body-text examples by tone: effects in the demerit category are red (`tone-debuff`); other effects are blue when they stack with themselves (`stacks: true`, `tone-stack`) and green when they do not (`stacks: false`, `tone-solo`); unverified or conflicting stacking keeps the default color in bold (`tone-unverified`). In relic tables, every rule label whose state is unverified or conflicting, and the 來源分歧 label of conflicting candidate values, is also bold (`tone-unverified`). A rule-line equivalent value (for example "equals Vigor +5") takes the effect's tone. Penalty phrases listed for a detail are red inside its tone. The rule label stating that a curse effect is required (`requiresCurse: true`) is red. Each relic page shows a color legend fixed to the bottom of the viewport (`<aside class="tone-legend" data-legend>`), rendered from `legend` in [public/data/common.json](public/data/common.json): each item has a `tone` (the class suffix), a `label`, and a `tip` shown on hover or focus; the items are 不可疊加 (green), 可疊加 (blue), 負面 (red), and 未核實 (bold). Tone classes MUST NOT be set by hand in HTML.
- When every tier detail of an effect ends with the same parenthetical note (for example （不適用於隱士、復仇者、執行者）), the page removes the note from each tier line and shows it once after them as 各等級：<note>; the data keeps the full text.
- `detail` holds the community detail text of an effect or tier: `en` is the source text verbatim and `zh` its translation. A detail whose number, item, or location contradicts the pinned game params is instead rewritten from the params in both languages and carries its own `sources`. An effect the dataset gives no detail gets one written from the params only when an explicit reference chain from its AttachEffectParam row gives the numbers and the detail tells the reader more than the name; otherwise it has no detail.

## Relic Data Generation

- `public/data/relics/*.json` are generated by [tools/import-relics.mjs](tools/import-relics.mjs) (`node tools/import-relics.mjs [category ...]`, run from the repo root); they MUST NOT be edited by hand. Edit the inputs and rerun:
  - [tools/relics-config.json](tools/relics-config.json): the pinned commit of each source, the category tree, the nightfarer columns, the status icon ID → icon key map (`null` = no matching licensed image), and the relic icon ID → icon key map.
  - [tools/relics-curated.json](tools/relics-curated.json): hand-curated effects matched to generated effects by `gameId`; their fields override generated values, and the script prints every overridden difference.
  - [tools/relic-details-zh.json](tools/relic-details-zh.json): the Traditional Chinese translation of each community detail, keyed by `gameId` and stored with its English original.
  - [tools/relic-stacking.json](tools/relic-stacking.json): self-stacking values for tiers the dataset leaves unknown, keyed by `gameId`, taken only from a community source that states them explicitly (the community sheet or Fextralife); each entry stores `stacks` (a boolean, or a `conflict` when the sources disagree), `sources`, and the quoted source rows in `quotes`. The script fills only unknown values and lists the sources in the effect's `sourcesFor["stacking.stacks"]`, together with the source of any tier the dataset already gives.
  - [tools/relic-details-params.json](tools/relic-details-params.json): details written from the game params, keyed by `gameId`; each entry stores the community `source` text (`null` when the dataset has no detail), the rewrite in `en` and `zh`, the param evidence in `params`, and optional `sources` (default `game-params`). A `gameId` MUST NOT appear in both detail files.
  - [tools/relic-penalties.json](tools/relic-penalties.json): penalty phrases inside the Traditional Chinese detail of a buff effect, keyed by the `gameId` that owns the detail; each value is an array of exact substrings (for example `"生命力 -5"`), written to `detail.penalties`. List every penalty in a detail, including each level's number.
- The script stops without writing when a curated effect, translation, effect or relic icon, character, or source reference (`sources`, `sourcesFor`, conflict candidates) has no match; when two curated effects map to the same `gameId`s; when a source field has an unknown enum value; when the English original of a translation or the `source` of a param rewrite differs from the source; when a `gameId` has both a translation and a param rewrite; when a param rewrite lacks `en`, `zh`, or `params`, has an empty `sources`, or has no matching effect; when an effect stores a rule field (`availability`, `requiresCurse`, `stacking`, `targets`, `stats`) both on the effect and on a tier; when an effect yields more than one different `targets` condition set or a `startMagicId` that no weapon slot references; when a stacking entry has no matching effect, targets a tier the dataset already gives, cites a source other than the community sheet or Fextralife, lacks one quote per source, or has an invalid `stacks` (a conflict needs at least two boolean candidates with different values, each citing listed sources); when a penalty entry is not a non-empty array of non-empty strings, has no matching detail, lists a phrase missing from the detail, or lists a phrase ending in a digit that matches only part of a longer number not covered by a longer listed phrase; or when either detail file, the stacking file, or the penalty file repeats a key or differs from its canonical `JSON.stringify` output with 2-space indentation. Fix the input instead of bypassing the check.
- The script generates `targets` from the SpEffectParam rows referenced by each effect's `passiveSpEffectId_1`–`_3`, together with the rows those reference through `analyzeSelfLevel1_effectId`–`3_effectId`: `triggerOnWepType`, `wepTypeTrigger` when `wepTypeTriggerCount` is above 0 (an equipped-count condition), and `weaponTypeDiscovery` give a `weaponType`; a `magicSubCategoryChange1` that is a defined school, with exactly one of `magParamChange` (sorcery) and `miracleParamChange` (incantation) set, gives a `spellType` and a `spellSchool`; exactly one of those flags with all three `magicSubCategoryChange` fields 0 and no weapon type gives a `spellType`; a `magicConsumptionRate` or `miracleConsumptionRate` other than 1 gives `sorcery` or `incantation`; a `startMagicId` gives `spell`, which MUST be a spell some weapon slot references. Only param values defined in `tags` produce a tag, and other effects get no `targets`. Identical conditions found more than once are kept once. `targets` is a rule field: it is stored on the effect when every tier has the same value, otherwise on each tier, and its source is recorded as `sourcesFor.targets: ["game-params"]`. The script stops when an effect yields more than one different condition set.
- The script generates `stats` from the SpEffectParam rows reached from each effect's `passiveSpEffectId_1`–`_3` and `permanentSpEffectId` through `replaceSpEffectId`, `cycleOccurrenceSpEffectId`, `atkOccurrenceSpEffectId`, `accumuOverFireId`, `accumuUnderFireId`, and `analyzeSelfLevel1_effectId`–`3_effectId`. A stat is changed when one of its `SpEffectParam` fields in a reached row differs from the neutral value (1 for a mapped field ending in `Rate`, otherwise 0), or when its `HeroStatusParam` field is not 0 in any of the rows X, X+1, … that follow without a gap from a reached row's `heroStatusModifier` X (the level points of a character effect). Effects that change no stat get no `stats`. The script stops without writing when a `param` value is not a non-empty list, a mapped field is not in the param table header, or a mapped field value in a reached row is not a number. `stats` is stored on the effect when every tier has the same value, otherwise on each tier, and its source is recorded as `sourcesFor.stats: ["game-params"]`.
- To update a source, change its commit in the config, rerun the script, and review the printed differences and the changed translations before committing. After a game param update, check every param rewrite against the new params.
- Translating a detail:
  - Every number keeps identical digits; never compute, round, or convert units.
  - Use the effect's official Chinese name and game terms; a term with no official Chinese name stays in English.
  - Translate source notes such as `TODO` as `（原文註記：……）`; where the source contradicts the effect name, translate literally and add `（原文如此）`. MUST NOT correct the source in a translation; a contradiction with the game params goes to the param rewrite file instead.

## Armament Data Generation

- `public/data/armaments/*.json` are generated by [tools/import-armaments.mjs](tools/import-armaments.mjs) (`node tools/import-armaments.mjs`, run from the repo root); they MUST NOT be edited by hand. Both import scripts read the pinned sources of [tools/relics-config.json](tools/relics-config.json) through [tools/sources.mjs](tools/sources.mjs), so relics, weapons, and spells always come from the same game params.
  - Weapons: every `EquipParamWeapon` row whose ID is a multiple of 10000, whose `wepType` has a `weaponType` tag, that has a name, whose `sortId` is not 9999999, and that an `EquipParamCustomWeapon` row targets (`targetWeaponId`, Nightreign's weapon generation param with weapon level and passive tables); plus every row that carries a spell (`equippedSpell_R1`/`equippedSpell_R2`), named or not. Base-game weapons absent from Nightreign, such as Dryleaf Arts and Dane's Footwork, keep `EquipParamWeapon` rows but have no `EquipParamCustomWeapon` row, so a name and a type alone do not show that a weapon is in the game.
  - Spells: every ID a weapon spell slot references. `spellType` comes from `Magic.ezStateBehaviorType`, and `spellSchool` from `Magic.subCategory1`/`subCategory2`, keeping only values with a defined tag (`[]` when none). A referenced ID with no `Magic` row gets `null` for both and is never classified from its name, its carrier, or the base-game list it appears in.
  - Names: the game params carry no names and no Nightreign text for weapons or spells is available, so names come from Elden Ring base-game text pinned as `erText` (soarqin/ERTools): weapons from `WeaponName` by weapon ID; spells only from the base-game sorcery and incantation lists by ID, never from `GoodsName`, whose IDs collide with key items. Blank, `%null%`, and `[ERROR]` entries are not names. An item without a name in both languages has `name: null`. Names record `sourcesFor.name: ["er-base-text"]`, and pages MUST say they are base-game reference names not confirmed for Nightreign.
  - Weapon values, only for named weapons: `attack` from `attackBasePhysics`, `attackBaseMagic`, `attackBaseFire`, `attackBaseThunder`, `attackBaseDark`; `scaling` from `correctStrength`, `correctAgility`, `correctMagic`, `correctFaith`, `correctLuck`; `critical` from `criticalAtkRate` (not `throwAtkRate`). They are raw params: Nightreign attack power also changes with level and rarity, and that calculation is not verified, so they MUST NOT be presented as in-game attack power or scaling grades. `passive` is the name of the `AttachEffectParam` row that `attachEffectId` references, looked up by its `attachTextId` in the Nightreign effect text (`game-text`); only the name is stored, and the values and conditions of its effects (through `passiveSpEffectId_1`–`3`, `onHitSpEffect`, and `permanentSpEffectId`) are not stored yet. `buildup` takes only the ailment buildup fields (`poizonAttackPower`, `diseaseAttackPower`, `bloodAttackPower`, `freezeAttackPower`, `sleepAttackPower`, `madnessAttackPower`, `curseAttackPower` as `poison`, `rot`, `blood`, `frost`, `sleep`, `madness`, `deathBlight`) of the `SpEffectParam` rows that `spEffectBehaviorId0`–`2` reference, skipping zero; other fields of those rows are not stored. Weapon skills, shield guard rates, and `heroID` are not stored.
  - Spell costs, only for spells with a `Magic` row: `cost` from `mp` and `stamina`; `chargeCost` from `mp_charge` and `stamina_charge`, `null` when both are 0. They are raw params before any cost reduction. The page shows `chargeCost` as is and MUST NOT present it as whether a spell can be charged: a non-zero value does not show how charged casting works, a 0 does not mean no cost, and the two lines must not be added. The channeled cost `consumeLoopMP_forMenu` is not stored.
  - Icons: the script looks up `File:ER SB Icon <weapon|shield|Spell> <English name without colons>.png` on Eldenpedia (`shield` for the three shield types) and sets `icon: { "src", "page" }` only when the file exists and its page carries `{{License|game}}`; otherwise `icon: null`. Lookups are cached in `tools/.cache/eldenpedia/files.json`. Afterwards run `python tools/fetch-icons.py`, which downloads every referenced icon missing from `public/images/` and downscales it to 96px.
- The script stops without writing the data files when a name exists in only one language, a carried spell is not included, a spell-carrying weapon's `wepType` has no tag, a spell's `ezStateBehaviorType` has no tag, a weapon value or spell cost is not a number, a weapon references a missing `SpEffectParam` or `AttachEffectParam` row, a fixed effect has no name in both languages, two hit effects of a weapon give the same ailment, two icons share a file name, or a source it cites is missing from common.json.

## Game Writing Rules

- When linking to an external resource, open it in a new window; navigating away from the current page is forbidden.
- Follow responsive web design (RWD) principles and support phones, tablets, desktops, and other devices. No page, including its header, needs horizontal scrolling at any screen width.
  - Tables: at a screen width of 900px or less, every table is shown row by row so that no table needs horizontal scrolling. Each row is a block whose first cell is its title; every other cell follows on its own line, with its column name in small text beside it. Wider screens and print keep the table. After the page is rendered, [public/render.js](public/render.js) copies each column header into the `data-label` of the cells in that column, except the first column, and sets the `table`, `rowgroup`, `row`, `columnheader`, and `cell` roles so the table keeps its semantics; the header row is hidden only visually. Every table MUST have one header row in `thead`, and every row MUST have as many cells as that header row; otherwise the page stops with an error.
  - Diagrams: build them from HTML boxes and text that wrap with the screen, not from fixed-width images, so that they need no horizontal scrolling and their text does not shrink to fit the screen.
- When mentioning an in-game item, agents MUST find the corresponding in-game image. The image source is [Eldenpedia](https://eldenring.wiki.gg/).
  - Use only images whose file page marks the license as a game asset (`{{License|game}}`); community edits (for example, filenames containing `Custom`) do not count as in-game images.
  - Download images to `public/images/`; the home page sources list their wiki file pages. An image larger than 96px may be downscaled to 96px; no other edits are allowed.
  - Each icon in [public/data/common.json](public/data/common.json) records its wiki file page in `page`; weapon and spell icons are stored in their item's `icon` in `public/data/armaments/` instead (see Armament Data Generation). The home page lists the file pages of every icon in common.json with `<span data-icon-sources>`, and states once that weapon and spell icons come from the Eldenpedia ER SB Icon series, whose file pages stay in the item data.
  - Images in the same layout position MUST keep the same size. Every image uses the `.icon` class, and its size is set only in `public/styles.css` by position, never adjusted on an individual image:
    - Inside a table: 48px (`td .icon`).
    - In a name list inside a table entry, including the 種類 column: 24px (`td .entry .icon`).
    - In body text: 24px (`.icon`).
    - When a new layout appears, first add a size rule for that position in `public/styles.css`.
    - The `width`/`height` attributes of `<img>` match the size for its position.
